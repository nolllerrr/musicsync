# PR 2: клиент и синхронизация групповых комнат

Ветка: `codex/group-rooms-sync`. База работы содержит протокол v1 и сервер для двух
участников. Групповая синхронизация проверяется на управляемых входах клиента;
настоящая сетевая комната на десять человек требует PR 1. Серверный протокол,
RoomRegistry, Electron UI, Sonata и установщик здесь не меняются.

## Изменения алгоритма

`RoomPlayer` принимает `IRoomConnection`. Каждый экземпляр читает только общее
`RoomState`, собственную роль, поколение подключения и свои часы, отправляет
собственный `PlayerReport`. Отчёты остальных слушателей не управляют его плеером.
Для остановки у конца песни допускается длительность из отчёта ведущего, как раньше.

Ключ обработки — `(generation, revision, role, retry)`. Роль включена в ключ и
проверку актуальности, поэтому передача управления работает даже без смены ревизии.
Изменение участников, их порядка, присутствия и отчётов не меняет этот ключ.

Один рабочий цикл выполняет одну команду плееру за раз. `Changed` отменяет токен
текущего наблюдения/применения при смене ревизии, роли, поколения или статуса
подключения. Подписка снимается после итерации; дополнительные фоновые задачи не
создаются. Обновление состава не отменяет загрузку. После уже переданной команды
сохраняется проверка актуальности: отмена не гарантирует откат совершённой команды,
но запрещает последующие шаги и успешный отчёт старой операции. В AgentPipe отмена
уже передаётся как `cancelEvaluation`, а Sonata проверяет актуальность перед мутацией.

Сохранены RTT-оценка часов, проверка точных ID, пересчёт позиции после загрузки,
порог 1200 мс, интервал повторной коррекции 8 секунд, ожидание следующей песни и
безопасная пауза неизвестного трека. Частоты остаются прежними: опрос плеера
450 мс в комнате / 900 мс без комнаты, ping каждые 2 секунды, публикация агента
каждые 250 мс при изменении состояния. Повторное подключение сохраняет прежний
backoff 1/2/4/8 секунд; серверные `error`/`ended` завершают соединение.

## Контракт состояния агента для PR 3

Одна JSON-строка через существующий `AgentPipe`, сериализация `Protocol.Json`.

```json
{
  "type": "state",
  "status": "connected",
  "role": "listener",
  "code": "0123456789ABCDEF01234567",
  "participants": [
    {
      "participantId": "42dbef53-a606-40e9-a9ed-ae41380fb331",
      "role": "leader",
      "connected": true,
      "report": null
    },
    {
      "participantId": "41c16775-2436-4db0-ae10-419074cd7edf",
      "role": "listener",
      "connected": true,
      "report": { "revision": 7, "kind": "failed", "detail": "track-unavailable" }
    }
  ],
  "selfParticipantId": "41c16775-2436-4db0-ae10-419074cd7edf",
  "capacity": 10,
  "peerConnected": true,
  "playbackError": "track-unavailable"
}
```

| Поле | Семантика |
|---|---|
| `status` | `connecting`, `connected`, `reconnecting`, `ended`, `idle`. |
| `participants` | Всегда массив публичных участников, включая отключённых, пока сервер сохраняет их места. Порядок не является идентичностью. |
| `participantId` | Публичный GUID от сервера. Сохраняется при resume, не зависит от роли. |
| `selfParticipantId` | Всегда присутствует: GUID собственного места или `null` до welcome / вне комнаты. |
| `capacity` | Всегда число: вместимость от сервера; `0` до welcome / вне комнаты. |
| `report` | Всегда присутствует у участника: индивидуальный `PlayerReport` либо `null`. |
| `role` | Собственная роль `leader` / `listener`, если известна. Может меняться. |
| `error` | Прежняя ошибка подключения, поле опускается при отсутствии. |
| `playbackError` | Прежняя локальная ошибка плеера, поле опускается при отсутствии. |
| `code` | Прежний код комнаты, если известен. |
| `swap` | Прежний контракт передачи роли; его изменение для групп относится к отдельной работе над ролями. |
| `peerConnected` | Временная совместимость старого UI. Для группы: подключён хотя бы один другой участник. PR 3 должен использовать `participants`. |

У `PlayerReport` сохраняются `revision`, `kind` (`applying`, `applied`, `corrected`,
`failed`, `unknown`, `waiting`) и необязательные `positionMs`, `durationMs`,
`sampleTime`, `rttMs`, `playback`, `applyMs`, `detail`. Временные отметки и позиции
даны в миллисекундах; `sampleTime` находится в системе серверного времени.
Отсутствующий отчёт не означает отсутствующего участника. Ошибка одного слушателя
отображается в его строке и не меняет общий режим воспроизведения.

При reconnect сохраняется последний известный список и собственный ID. После
`ended` или `idle` список пуст, ID `null`, capacity `0`. Без новых снимков и ошибок
агент не публикует одинаковое состояние на каждом тике.

До PR 1 невозможно восстановить реальные публичные ID из v1. Поэтому адаптер
совместимости возвращает `participants: []`, `selfParticipantId: null`,
`capacity: 2` после welcome и прежний `peerConnected`. Это явное ограничение
текущей ветки, а не полноценная поддержка группового транспорта.

## Сочетание с PR 1

Единственная зависимая реализация клиента — `src/MusicSync.Core/RoomMembership.cs`.
После объединения контракта PR 1 заменить её содержимым
`docs/group-rooms-pr1-RoomMembership.cs.txt`. Это адаптер готовых типов PR 1,
он не определяет серверные DTO и не реализует сервер. Он читает:

- `RoomView.Participants`: `ParticipantId`, `Role`, `Connected`, `Report`;
- `RoomView.Capacity`;
- `ServerMessage.ParticipantId` из welcome, с сохранением при последующих snapshot.

Welcome применяется до первого pong. Промежуточные snapshot обновляют уже
созданный `ConnectionView`, поэтому не теряют собственный ID. В дальнейшем роль
вычисляется по GUID собственного участника, а не по индексу массива.

При совмещении также нужны следующие шаги:

1. Принять из PR 1 новые DTO, версию и увеличение допустимого серверного кадра
   в `Wire`: 4096 байт v1 может быть недостаточно для десяти подробных отчётов.
   Нельзя просто отключать строгую десериализацию неизвестных полей.
2. Адаптировать создание RoomView в двух новых тестовых фикстурах:
   `PlayerGroup.Add` и `AgentStateTests.PipePublishesAllPublicParticipantsAndSelfIdentity`.
   Вместо `new(state, leader, listener)` использовать
   `new(state, participants, 10)` с публичными участниками PR 1. Двухместные
   старые тесты согласовать с изменениями тестов из PR 1.
3. Запустить настоящий сервер PR 1 и десять RoomConnection: проверить welcome,
   fan-out, индивидуальные report, уход/возврат с тем же GUID, отсутствие
   слушательских action, лимит вместимости и снимки большого размера.
4. Проверить передачу роли с PR, который меняет управление ролями. Этот PR 2
   проверяет поведение плеера после изменения роли, но сохраняет старую команду
   взаимного обмена и не вводит групповую политику выбора нового ведущего.

Не объединять клиент с сервером v2, оставив v1-адаптер: его пустой список и
отсутствующий self ID предназначены только для текущей двухместной базы.

## Проверки

`GroupPlayerTests` использует управляемые `IRoomConnection`, общий `RoomState`,
десять независимых RoomPlayer, фейковые плееры и `PollTime`. Ожидание регистрации
таймеров служит барьером окончания опроса; время продвигает тест. Реальные тайм-ауты
применяются только как защита от зависания. Сетевой сервер для групп не имитируется.

Проверяются track/seek/play/pause для десяти клиентов, медленная и неисправная
загрузка, частые snapshot и перестановка участников, presence во время загрузки,
отмена старой ревизии, reconnect после 90 секунд, новый слушатель посреди песни,
смена роли без смены ревизии и во время загрузки, временное исчезновение ведущего,
unknown-track и ожидание следующей песни. AgentStateTests проверяет JSON через
настоящий AgentPipe, стабильные публичные поля и очистку при выходе.

Существующие сетевые PlayerTests и ServerTests остаются регрессией двухместного
режима, включая RTT, cooldown, восстановление, native playback и обмен ролями.
