# Групповые комнаты: протокол v2

## Состояние и идентичность

Комната содержит один общий `RoomState` и 1–10 мест. Ровно один участник — `leader`, остальные — `listener`. `Participant` содержит только публичный `participantId` (GUID), `role`, `connected`, `report` (явный null при отсутствии). Порядок массива не является контрактом. Секретный 256-битный токен никогда не включается в снимок, URL или журнал; серверный индекс `token → (room, seat)` не зависит от роли.

`create` содержит `version: 2`, `type`, `token`. `join` и `resume` дополнительно содержат `roomId`: 24 заглавных hex-символа. `welcome` возвращает собственный `participantId`, `role`, полный `room`. Последующие `snapshot` содержат `role` получателя и тот же общий `room` без корневого `participantId`.

| Поле room | Содержание |
|---|---|
| `state` | `roomId`, `revision`, `selection`, `track` (ID альбома/записи или null), `playback`, `positionMs`, `serverTimestamp`, `unknown` |
| `participants` | От одного до `capacity` публичных участников, включая отключённые зарезервированные места |
| `capacity` | Целое 1–10, включая ведущего |
| `transfer` | Необязательный адресный запрос передачи управления |
| `swap` | Необязательное согласование парной смены ролей для совместимости |

Возврат с прежним токеном сохраняет место и публичный ID, заменяя прежнее соединение. Старое соединение больше не может менять состояние или отключить заменившее его. Явный выход слушателя сразу освобождает место; разрыв резервирует его на `GraceSeconds` (90 по умолчанию). Разрыв ведущего сохраняет комнату до истечения grace, явный выход ведущего завершает комнату для всех. Перезапуск клиента или сервера не сохраняет токены/комнаты на диск.

## Команды и отчёты

Только ведущий отправляет `action`: непустой GUID `id` и `action` с `baseRevision`, видом и соответствующими параметрами. Старые ревизии получают `stale-revision`, слушатели — `leader-only`. Повтор принятого ID подтверждается без повторного изменения. История последних 128 ID очищается при смене ведущего, чтобы старые команды не считались подтверждёнными в новой эпохе управления.

`report` содержит только собственный `PlayerReport` текущей ревизии. Позиция и длительность ограничены 24 часами, RTT — 30 секундами, применение — 120 секундами. `detail` — необязательный машинный код до 64 ASCII-символов `[a-z0-9-]`; произвольный текст ошибок не передаётся. Для Applied/Corrected нужны позиция, длительность, отметка времени и режим; временная отметка должна находиться в пределах ±60 секунд от приёма. Устаревшие отчёты игнорируются.

Новая ревизия очищает отчёты всех участников; разрыв/возврат — только соответствующего места. Состав, присутствие, отчёты и запрос передачи не повышают ревизию. Клиент применяет также снимки с равной ревизией, не перезапуская плеер.

Отчёты помечают комнату изменённой. Таймер раз в 250 мс рассылает один общий снимок всех накопленных отчётов. Повтор неизменившегося отчёта рассылки не вызывает. Команды, состав и смена ролей рассылаются немедленно и включают последние отчёты. Таким образом, десять источников отчётов создают до четырёх рассылок комнаты в секунду (до 40 доставок), вместо рассылки на каждый отчёт.

## Передача управления

Сервер выбирает `musicsync.leadership-transfer`, если клиент его предложил; иначе допускается `musicsync.roleswap` или соединение без расширений. Участники адресной передачи должны согласовать новое расширение и оставаться подключёнными.

| Команда | Дополнительные поля |
|---|---|
| `transfer-leadership` | `id`, `targetParticipantId` выбранного слушателя |
| `accept-leadership` | `id`, `transferId` актуального запроса |
| `cancel-leadership` | `id`, `transferId`; инициатор отменяет, адресат отклоняет |

`room.transfer` содержит серверный GUID `id`, `initiatorParticipantId`, `targetParticipantId`, `expiresAt` по монотонным часам сервера. Только текущий ведущий создаёт запрос, только адресат подтверждает. В комнате одновременно один запрос; конкурирующий получает `leadership-transfer-pending`. Чужое подтверждение получает `leadership-transfer-target-only`, отмена — `leadership-transfer-forbidden`.

Проверка и изменение выполняются атомарно под блокировкой реестра. При подтверждении прежний ведущий становится слушателем, адресат — ведущим, ревизия повышается, отчёты и история принятых команд очищаются. Трек, режим и текущая вычисленная позиция сохраняются; позиция привязывается к текущему времени. ID и токены мест не меняются. Повтор/старый ID получает `leadership-transfer-stale`.

Запрос действует 30 секунд. Истечение блокирует подтверждение сразу, даже до обслуживания таймера. Разрыв, выход или замена соединения инициатора/адресата отменяет согласие; возврат требует нового запроса. Другие участники могут входить и выходить, не отменяя адресный запрос. Отключение ведущего не назначает преемника автоматически.

Прежняя парная `swap-roles` работает при двух подключённых участниках с поддержкой соответствующего расширения. При трёх и более местах возвращается `role-swap-group-unsupported`. Во время адресного запроса парный обмен недоступен. Новый UI использует адресную передачу и для двух участников.

## Версия и ограничения

Сервер и агент используют `Protocol.Version = 2`. Клиенты v1 получают `protocol-version` до выделения места, без группового снимка. Сервер и установленные клиенты нужно обновлять совместно; даже вместимость 2 не включает v1. JSON использует camelCase и строковые перечисления; неизвестные/повторные поля и неподходящие для вида команды идентификаторы отклоняются.

| Настройка | По умолчанию | Допустимо |
|---|---:|---:|
| `Sync:MaxParticipantsPerRoom` | 10 | 1–10 |
| `Sync:MaxRooms` | 16 | 1–128 |
| `Sync:MaxConnections` | `MaxRooms × MaxParticipantsPerRoom + 16` = 176 | 2–1296 |
| `Sync:GraceSeconds` | 90 | 5–600 |
| `Sync:MaxRoomsPerSource` | 4 | 1–128 |
| `Sync:MaxRoomCreationsPerSource` | 8 | 1–128 |
| `Sync:RoomCreationWindowSeconds` | 60 | 1–3600 |

По умолчанию 160 мест и 16 дополнительных подключений позволяют заменять соединения при полной занятости. Явный меньший `MaxConnections` допускается как намеренный глобальный предел; новые подключения получают HTTP 503. Compose явно задаёт 176/16/10. Максимальные настройки требуют отдельной оценки ресурсов VPS: проверка локальных соединений не является нагрузочным испытанием продакшена.

Входящий кадр ограничен 4096 байтами, серверный — 8192, в том числе при отправке. Тест максимально заполненного `welcome` (10 отчётов, предельные числа и ID трека, адресный запрос) даёт **4220 байт**. Старых 4096 недостаточно, а 32768 из серверной ветки избыточны для компактного контракта. Отдельный тест передаёт независимые отчёты десяти клиентов через настоящий WebSocket.

Очередь отправки — 48 сообщений на соединение; сетевой ввод-вывод и сериализация выполняются вне блокировки. Переполнение и тайм-аут 4 секунды отключают только медленного клиента. Ограничение входящих сообщений — 20/сек на соединение, рукопожатие — 6 секунд, ожидание сообщения — 12 секунд. При 176 соединениях максимум 8448 записей очередей; снимок участников одной рассылки разделяется получателями, а не копируется целиком для каждого.

История созданий ограничена 8192 записями. Квота источника использует нормализованный TCP IP; `X-Forwarded-For` учитывается только от явно настроенного `Sync:TrustedProxy`. Удаление комнаты освобождает активную квоту, но не квоту созданий за окно. Вход и восстановление существующего места не расходуют квоту создания.

В C# остаются `[JsonIgnore]`-проекции `RoomView.Leader`/`Listener` для парного `SyncClock.Difference` и регрессионных тестов. Они не входят в wire-контракт. Групповой плеер получает отчёт ведущего по роли, UI — список участников; отдельный дублирующий DTO участника удалён.
