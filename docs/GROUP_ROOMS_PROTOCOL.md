# Group Rooms: сервер и протокол v2 (PR 1)

## Модель и границы PR

Комната содержит один общий `RoomState` и от одного до десяти мест. Ровно одно место имеет роль `leader`, остальные — `listener`. Сервер хранит места в списке; приватный индекс `token → (room, seat)` обеспечивает восстановление независимо от роли. У каждого места собственные GUID, роль, соединение, отчёт плеера и срок резервирования. Публичные DTO не содержат токенов.

Операции над реестром последовательны под короткой общей блокировкой. Вход, выход, восстановление, отчёты и команды воспроизведения формируют полный снимок для всех подключённых участников. Под блокировкой выполняется только неблокирующая постановка в очереди; сериализация, WebSocket I/O и отмена сетевых операций выполняются отдельно. Снимок не изменяется после постановки в очередь. Медленный клиент с заполненной очередью отключается независимо от остальных.

UI, групповой расчёт синхронизации и новый механизм передачи управления в этот PR не входят.

## Точный контракт для PR 2–4

Все JSON-имена — camelCase, значения перечислений — строки camelCase. GUID сериализуется строкой в формате `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`. Неизвестные и повторные JSON-свойства, числовые значения перечислений и некорректные обязательные поля отклоняются.

| C# | JSON | Значение |
|---|---|---|
| `RoomView.State` | `room.state` | Один общий `RoomState`, структура и семантика v1 сохранены. |
| `RoomView.Participants` | `room.participants` | `IReadOnlyList<Participant>`, от 1 до `capacity` элементов; отключённые зарезервированные места включены. |
| `Participant.ParticipantId` | `participantId` | Обязательный публичный GUID, уникальный для места; сохраняется при восстановлении и парной смене ролей. |
| `Participant.Role` | `role` | `leader` или `listener`; в списке всегда ровно один `leader`, даже при его временном отключении. |
| `Participant.Connected` | `connected` | Обязательный bool; отражает присоединённое сервером соединение, а не состояние локального плеера. |
| `Participant.Report` | `report` | Независимый `PlayerReport` текущей ревизии или явный JSON `null`. |
| `RoomView.Capacity` | `room.capacity` | Обязательный int от 1 до 10, заданный настройкой сервера. Ведущий занимает одно место. |
| `RoomView.Swap` | `room.swap` | Прежний контракт парного согласования. Поле отсутствует, когда операция недоступна. |
| `ServerMessage.ParticipantId` | `participantId` в корне | Собственный GUID получателя, обязателен в `welcome`; в остальных сообщениях отсутствует. |
| `ServerMessage.Role` | `role` в корне | Роль получателя в `welcome` и каждом `snapshot`; может измениться при парной смене ролей. |
| `ConnectionView.ParticipantId` | Только C# | `RoomConnection.View.ParticipantId` сохраняет собственный GUID из `welcome`, включая переподключение. |

Пример создания комнаты (GUID и код иллюстративные):

```json
{
  "version": 2,
  "type": "welcome",
  "role": "leader",
  "room": {
    "state": {
      "roomId": "0123456789ABCDEF01234567",
      "revision": 0,
      "selection": 0,
      "track": null,
      "playback": "paused",
      "positionMs": 0,
      "serverTimestamp": 1800000000000,
      "unknown": false
    },
    "participants": [
      {
        "participantId": "ea770ace-e0de-4ff1-8c5a-d67bc14227ad",
        "role": "leader",
        "connected": true,
        "report": null
      }
    ],
    "capacity": 10
  },
  "participantId": "ea770ace-e0de-4ff1-8c5a-d67bc14227ad"
}
```

`snapshot` содержит тот же полный `room` и роль получателя, без корневого `participantId`. Порядок участников не является контрактом: искать себя следует по собственному GUID, ведущего — по роли. Нельзя использовать индекс массива или токен в качестве публичной идентичности. `ParticipantId` не даёт права на восстановление или управление; для входа используется только секретный токен.

Изменение состава, подключения и отчёта не увеличивает `state.revision`. Клиенты должны применять такие снимки и при равной ревизии. `RoomState` содержит прежние поля `roomId`, `revision`, `selection`, `track`, `playback`, `positionMs`, `serverTimestamp`, `unknown`; позиция и ревизия общие для всех. Время и позиция передаются в миллисекундах.

Отчёт относится только к отправителю. Сервер принимает отчёты текущей ревизии с допустимой временной отметкой; остальные игнорирует. Новая ревизия очищает все отчёты, отключение или восстановление очищает только отчёт соответствующего участника. Оставшиеся поля `PlayerReport` и правила их проверки не меняются.

В C# временно оставлены вычисляемые `[JsonIgnore]`-свойства `RoomView.Leader` и `RoomView.Listener`, чтобы существующие клиент и парный расчёт продолжали собираться. `Leader` находит место по роли; `Listener` возвращает реального слушателя только при двух местах, иначе отключённую заглушку с `Guid.Empty`. Эти свойства отсутствуют на проводе. PR 2–3 должны использовать `Participants`, включая собственный GUID, и заменить парное отображение/расчёт для группы.

## Вход, восстановление и завершение

Форма `ClientMessage` сохранена: версия 2, `type` = `create`, `join` или `resume`, секретный `token`, а для `join`/`resume` — `roomId`. Код — 24 заглавных hex-символа (96 бит), токен — 64 (256 бит). Передача через URL запрещена. Сервер не возвращает токен ни отправителю, ни другим участникам и не пишет его в журнал.

- `create` с новым токеном создаёт ведущего. Повтор `create` с прежним токеном ведущего возвращает прежнюю комнату и GUID.
- `join` с новым токеном создаёт слушателя, если есть место. При заполнении — `error: room-full` и закрытие соединения.
- Повтор `join` с токеном существующего слушателя этой комнаты или `resume` с токеном любого её участника восстанавливает то же место и GUID даже в заполненной комнате.
- Повтор с действующим токеном заменяет предыдущее соединение. Его поздние команды и `Detach` не влияют на новое соединение. Тот же токен не создаёт второе место или место в другой комнате (`invalid-session`).
- `resume` с неизвестным, покинувшим комнату или истёкшим токеном возвращает `room-unavailable`. После окончательного освобождения места новый `join` создаёт новую публичную идентичность.
- `leave` слушателя подтверждается `result` и сразу освобождает место. При обрыве соединения место остаётся занятым на `Sync:GraceSeconds` (по умолчанию 90). Другой токен не может занять резерв.
- `leave` ведущего завершает комнату для всех (`ended: leader-left`). При его обрыве комната сохраняется до конца grace period; затем все слушатели получают `ended: leader-timeout`. Автоматического назначения нового ведущего нет.

Очистка выполняется каждые пять секунд и перед каждым входом: физическое удаление и уведомление об истечении могут запаздывать до пяти секунд, но новый вход проверяет срок сразу. Отсчёт начинается после обнаружения обрыва. При молчаливой потере сети действует прежний тайм-аут получения 12 секунд. Состояние не переживает перезапуск сервера.

Только ведущий принимает `action`. Слушатель получает `result: leader-only`, в том числе при повторе уже принятого ID. Общая базовая ревизия защищает от устаревших команд (`stale-revision`); последние 128 принятых ID комнаты подтверждаются без повторного изменения.

## Парная смена ролей до PR 4

Подпротокол `musicsync.roleswap`, запрос `swap-roles`, подтверждение, окно 30 секунд и ошибки `role-swap-stale`/`role-swap-unavailable` сохранены для ровно двух мест с поддерживающими операцию подключёнными клиентами. Роли меняются внутри существующих мест: GUID и токены остаются у прежних участников. Ревизия увеличивается, отчёты очищаются.

При трёх и более местах, включая отключённые резервы, `swap` отсутствует, а запрос возвращает `result: role-swap-group-unsupported`. Вход, выход и переподключение сбрасывают прежнее согласие. После возвращения к двум подключённым участникам создаётся новый `swap.id`; старый не может подтвердить новую операцию. Адресная передача управления в группе относится к PR 4.

## Миграция версии

`Protocol.Version = 2`. Сервер принимает только v2. На первое сообщение v1 или другой версии он отвечает `{"version":2,"type":"error","error":"protocol-version"}` и закрывает соединение **до** создания/восстановления места. Групповой снимок старому клиенту не отправляется. Это намеренно несовместимое обновление; сервер и клиенты нужно обновлять совместно. Смешанный режим v1/v2 и преобразование группы в пару не поддерживаются.

Клиент C# в этой сборке использует v2 и принимает увеличенные снимки. Выпущенная Electron-панель и старые бинарные клиенты v1 требуют обновления в клиентских PR. Ограничение комнаты двумя местами не включает поддержку v1.

## Лимиты и память

| Настройка | По умолчанию | Допустимые значения |
|---|---:|---:|
| `Sync:MaxParticipantsPerRoom` | 10 | 1–10 |
| `Sync:MaxConnections` | 32 | 2–256 |
| `Sync:MaxRooms` | 16 | 1–128 |
| `Sync:GraceSeconds` | 90 | 5–600 |
| `Sync:MaxRoomsPerSource` | 4 | 1–128 |
| `Sync:MaxRoomCreationsPerSource` | 8 | 1–128 |
| `Sync:RoomCreationWindowSeconds` | 60 | 1–3600 |

Некорректные настройки отклоняются при запуске. Глобальные лимиты соединений и комнат не увеличиваются автоматически: например, для одновременного подключения всех участников 16 полных комнат потребуется осознанно задать `MaxConnections=160`. При исчерпании глобальных соединений новый WebSocket получает HTTP 503; при лимите комнат — `server-full`.

Создание ограничивается реальным IP TCP-подключения (IPv4-mapped адрес нормализуется), включая комнаты с отключённым ведущим. `X-Forwarded-For` для этого не используется. За NAT или обратным прокси адрес будет общим; лимиты на источник следует выбирать с учётом схемы развёртывания. Ограничение возвращает `room-creation-limited`, не мешает входу слушателей и повторному использованию существующего токена. Удаление комнаты освобождает активную квоту, но не квоту созданий за скользящее окно. В исходной ревизии этого worktree ограничения создания по IP отсутствовали; здесь они добавлены в рамках требований PR 1.

Размеры структур ограничены независимо:

- Мест и записей токенов — не более `MaxRooms × MaxParticipantsPerRoom`: 160 по умолчанию, 1280 при максимальных настройках.
- Очередей — не более `MaxConnections`, по 48 сообщений каждая: 1536 ожидающих сообщений по умолчанию, 12288 при максимуме. Один снимок участников разделяется очередями одной рассылки; сериализация происходит при отправке.
- Истории команд — 128 GUID на комнату. Истории успешных созданий — максимум 8192 записи и не больше 8192 счётчиков источников, очищаемых по окну. При её заполнении новые создания отклоняются, существующие сессии продолжают работать.
- Клиентское сообщение — до 4096 байт, серверное — до 32768 байт. `Detail` отчёта ограничен 350 UTF-16 символами. Тест заполняет десять отчётов Unicode и проверяет фактическую передачу снимка больше 4096 байт и его размер в пределах 32768.
- Прежние ограничения: 20 входящих сообщений в секунду на соединение, 6 секунд на рукопожатие, 12 на ожидание сообщения, 4 на отправку. Переполнение очереди и тайм-аут отправки закрывают только соответствующее соединение с последующим резервированием места.

При отчётах всех участников число доставок растёт квадратично от размера комнаты; предел 10 и ограниченные очереди ограничивают накопление памяти. Нагрузочный бенчмарк не выполнялся; автоматический тест отдельно проверяет, что переполнение очереди одного участника не мешает доставке остальным.

## Проверки

```powershell
dotnet restore MusicSync.slnx
dotnet build MusicSync.slnx --no-restore --configuration Release --verbosity minimal
dotnet test tests/MusicSync.Tests/MusicSync.Tests.csproj --configuration Release --no-restore --logger 'trx;LogFileName=group-rooms.trx' --verbosity minimal
```

Серверные тесты используют настоящий Kestrel и WebSocket: создание; десять участников и отказ одиннадцатому; выход и новое место; восстановление и конфликт токена; рассылка всем; независимые отчёты; обрыв слушателя и ведущего; явное завершение; истечение резервов; запрет действий слушателя; гонка за последнее место; отказ v1; парная смена ролей и её отключение для группы; ограничения IP и соединений. Детерминированные проверки реестра покрывают переполнение очереди и попытки действий со старого заменённого соединения. Прежние тесты воспроизведения и восстановления также сохраняются.

Release-сборка проверяется на Windows с .NET 10, включая WPF, агент и установщик. Ручная проверка реального плеера, панели Electron и нескольких ПК остаётся за рамками серверного PR.

Результат на Windows / .NET SDK 10.0.403: Release-сборка всех восьми проектов успешна без предупреждений и ошибок; 49 тестов пройдены, пропущенных нет. TRX сохраняется в `tests/MusicSync.Tests/TestResults/group-rooms.trx` (локальный артефакт, исключён из Git).
