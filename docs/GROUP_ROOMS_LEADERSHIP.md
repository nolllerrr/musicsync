# PR 4 — адресная передача управления: подготовительная часть

Ветка: `codex/group-rooms-leadership`, отдельный worktree от `454aa3e`.

Групповая передача **ещё не включена на сервере**. В исходной ветке нет PR 1:
`Participant` не содержит ID, а `RoomView` содержит только `Leader` и `Listener`.
В соответствии с разделом 8 задачи подготовлены изолированные правила, контракт,
клиентские методы и тесты. Временная групповая модель в production не добавлена.
Ветки PR 1–3 не объединялись; PR не открыт.

На 12 ноября 2026 года в соседнем worktree `codex/group-rooms-server` наблюдалась
незакоммиченная модель PR 1: `Guid ParticipantId`, `RoomView.Participants`, `Capacity`,
`ServerMessage.ParticipantId`, протокол v2. Это ориентир для интеграции, а не стабильная
зависимость. Перед подключением нужно сверить окончательный коммит PR 1.

## Что реализовано

- `LeadershipTransfer` с ID запроса, ID инициатора и адресата, серверным сроком.
- Дополнительные поля `RoomView.Transfer`, `ClientMessage.TargetParticipantId`
  и `ClientMessage.TransferId`. Пустые поля отсутствуют в JSON старых сообщений.
- `RoomConnection.TransferLeadershipAsync`, `AcceptLeadershipAsync`,
  `CancelLeadershipAsync` используют существующие очередь запросов, корреляцию
  ответов, поколение подключения и тайм-аут. Неопределённая доставка не повторяется.
- Подпротокол `musicsync.leadership-transfer`. Клиент отправляет новые команды
  только после его фактического выбора сервером. Текущий сервер выбирает прежний
  `musicsync.roleswap`; новые методы возвращают `leadership-transfer-unavailable`.
- Чистая `LeadershipTransferPolicy`: проверка инициатора и адресата, один активный
  запрос, отказ постороннему, истечение ровно на границе 30 секунд, отмена инициатором
  или отказ адресатом, инвалидирование после отключения одного из них. Отключение
  постороннего не влияет на запрос. Время передаётся явно, без ожидания таймеров.
- `AdvancePlaybackEpoch` подготавливает новую ревизию, сохраняя трек, выбор,
  Play/Pause и позицию, спроецированную на момент передачи. Этот helper пока
  не подключён к реестру; прежний RoleSwap сохраняет прежнее поведение.
- Текущий сервер явно отклоняет новые поля в старых командах и рукопожатии,
  чтобы расширение DTO не ослабило строгую проверку протокола.

Политика не хранит комнаты, участников или роли и не выполняет атомарную смену
ведущего. Успешная проверка сама по себе не расходует запрос: это обязанность
реестра под его блокировкой. Многократный вызов чистой проверки не является
доказательством безопасности конкурентных подтверждений на будущем сервере.

Изменённые файлы:

- `src/MusicSync.Core/LeadershipTransfer.cs`, `Protocol.cs`, `RoomConnection.cs` —
  контракт и клиент.
- `src/MusicSync.Server/LeadershipTransferPolicy.cs`, `RoomRegistry.cs`,

## Контракт интеграции

| Команда | Дополнительные обязательные поля |
|---|---|
| `transfer-leadership` | `id`, `targetParticipantId` |
| `accept-leadership` | `id`, `transferId` |
| `cancel-leadership` | `id`, `transferId` |

`id` — ID команды для существующего `result`; `transferId` — отдельный,
выданный сервером ID предложения. Все ID имеют тип `Guid`, пустой GUID запрещён.
Команды не содержат токенов, комнаты, роли, ID инициатора, действия плеера,
отчёта, ping или `swapId`. Отказ выбранного слушателя — `cancel-leadership`.

Ошибки: `leader-only`, `leadership-transfer-invalid-target`,
`leadership-transfer-unavailable`, `leadership-transfer-pending`,
`leadership-transfer-stale`, `leadership-transfer-expired`,
`leadership-transfer-target-only`, `leadership-transfer-forbidden`.
Клиент дополнительно возвращает `offline`, `invalid-command`, `delivery-unknown`.

Срок — абсолютное значение серверных монотонных часов в миллисекундах,
`now + 30_000`; подтверждение допустимо только при `now < expiresAt`.
Очистка по таймеру не заменяет проверку срока непосредственно при подтверждении.

### Версия и совместимость с PR 1

В подготовительной ветке `Protocol.Version` остаётся 1: формат действующих
сообщений не изменён, новая возможность закрыта согласованием подпротокола.
При интеграции нужно сохранить v2 из PR 1; отдельная v3 для этого опционального
расширения не нужна **при соблюдении всех следующих условий**:

1. Сервер выбирает новый подпротокол только после подключения обработчиков.
2. Инициатор и адресат поддерживают адресную передачу.
3. Для каждого клиента без нового подпротокола сервер отправляет
   `RoomView` с `Transfer = null`, включая `welcome` и все рассылки. Старые
   v2-клиенты строго отклоняют неизвестные поля; одного согласования команд
   недостаточно. Остальные участники всё равно получают обновлённые роли в v2.
4. Все клиенты получают один фактический список участников PR 1; отдельная
   модель или список для передачи не создаются.

Если скрытие поля по возможностям клиента не будет реализовано, контракт нельзя
объявлять совместимым: потребуется общее обновление версии протокола.

### Подключение к реестру после PR 1

Всё ниже выполняется внутри существующего `gate`, без сетевого ожидания:

1. Разрешить `peer` в актуальное место по серверной сессии и проверить
   `seat.Peer == peer`. ID вызывающего берётся из этого места. Проверка
   `isConnected(id)` ищет место только в текущей комнате и требует актуальный
   peer без запрошенного отключения; ID из клиентского JSON не является сессией.
2. Для создания проверить форму команды, возможности двух клиентов и вызвать
   `Create` с фактическим ID ведущего. Хранить единственный `Room.Transfer`.
   Конкурентное создание под той же блокировкой должно увидеть pending.
3. Для подтверждения проверить ID, срок, текущего ведущего и адресата через
   `Accept`. Затем в той же критической секции поменять роли/ссылку на ведущего,
   обновить роли активных peer, сохранить соответствие токенов местам PR 1,
   вызвать `AdvancePlaybackEpoch`, очистить отчёты **всех** участников,
   очередь принятых playback-команд и использованный запрос. Только затем
   разослать снимок всем. Повторное подтверждение видит отсутствующий ID.
4. Старый и новый ведущие проходят обычную серверную проверку роли и базовой
   ревизии при каждом действии. Очередь старых ID команд не должна обходить
   новую ревизию. Отчёты предыдущей ревизии игнорируются.
5. Применить `KeepPending` при обслуживании таймера. При выходе, отключении
   или замене соединения инициатора/адресата очистить запрос сразу, **до**
   присоединения нового peer. Это обязательно и при resume с прежним ID:
   новая сессия не наследует согласие старой. Само возвращение `isConnected`
   в true не должно восстанавливать старый запрос.
6. `Cancel` очищает запрос и рассылает снимок, не изменяя ревизию воспроизведения
   и роли. Явный выход ведущего завершает комнату; сетевой обрыв сохраняет
   grace-период PR 1 без автоматического назначения ведущего.
7. Не вводить независимый путь присваивания ролей: выделить общий атомарный
   commit для совместимого двухместного RoleSwap и адресного предложения.
   Их pending-запросы должны взаимно исключаться. Сохранить тесты старого
   сценария, включая инициацию RoleSwap слушателем.

### Зависимость от PR 2–3

В `RoomConnection` нужно сохранить собственный `ParticipantId` из PR 1 и
изменения восстановления из PR 2. При конфликте в `RoomView` добавить только
`Transfer` к реальному списку `Participants`; проекции парной модели не переносить.
В `RoomRegistry` защитный запрет новых полей заменить строгой проверкой формы
каждой из трёх новых команд, оставив запрет этих полей в остальных командах.

Агент PR 2 должен передавать текущий ID, список участников и предложение
с `remainingMs = clamp(expiresAt - clock.Now, 0, 30_000)`.
Интерфейс PR 3 должен показывать ведущему выбор подключённого слушателя,
подтверждение отправки, ожидание и отмену. Только адресат видит принятие
и отказ; посторонние видят обновление ролей без кнопок чужого подтверждения.
Таймер не является источником полномочий. Существующие стили Яндекс Музыки
сохраняются. Агент и renderer этой подготовительной веткой не меняются.

## Подготовленное описание PR

**Название:** Prepare targeted leadership transfer contracts and validation

Текущий RoleSwap адресует единственного второго участника и не позволяет выбрать
адресата в групповой комнате. Добавлены адресное предложение со сроком 30 секунд,
проверки прав и клиентские методы за согласованием возможностей сервера.
Текущий двухместный сценарий продолжает работать без изменения поведения.

Это подготовительная часть по разделу 8 задачи: PR 1 отсутствует в базе.
Атомарное подключение к реестру участников, агент PR 2, интерфейс PR 3 и проверки
десяти клиентов остаются обязательными до готовности полной функции.
Проверки: сборка без предупреждений, 95 .NET-тестов, 15 JavaScript-тестов,
синтаксис JavaScript и diff-check. Добавленные тесты покрывают политику, WebSocket-
контракт и смену роли при незавершённых load/seek. Полная матрица и правила
совместимости приведены выше. Ручная проверка на нескольких ПК не выполнена.
