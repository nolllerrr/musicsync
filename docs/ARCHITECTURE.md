# Архитектура MusicSync

| Проект | Назначение |
|---|---|
| `MusicSync.Core` | Контракты, клиентский WebSocket, часы, рабочий цикл плеера и контракт `IPlayer`. |
| `MusicSync.Server` | ASP.NET Core, `/health`, `/ws`, комнаты и их снимки в памяти. |
| `MusicSync.Yandex` | Адаптеры официальной Яндекс Музыки. Обычный режим использует GSMTC и UI Automation, Sonata управляет плеером через локальный CDP. |
| `MusicSync.Client` | Windows WPF, вход в комнату, управление, состояние, настройки и диагностика. |
| `MusicSync.Tests` | MSTest, настоящий Kestrel на временных loopback-портах, сетевой обрыв и имитируемые плееры. |

## Состояние и восстановление

Клиент продолжает работу в трее после закрытия окна. Ведущий управляет официальным плеером. Клиент публикует смену песни с проверенными ID, наблюдаемые Play/Pause и перемотку за пределы порога. Слушатель применяет эти ревизии. Ведущий подтверждает состояние своего плеера без обратной команды. При восстановлении той же ревизии изменения, сделанные ведущим во время обрыва, передаются комнате.

При создании сервер генерирует 96-битный код комнаты. В комнате один ведущий и до девяти слушателей, один общий `RoomState`. Место содержит публичный GUID `ParticipantId`, роль, соединение и независимый `PlayerReport`. Клиент создаёт секретный 256-битный токен своего места и держит его в памяти. Индекс токенов ссылается на конкретное место, а не на роль; токен отсутствует в снимках и журналах. Рукопожатие `create`, `join` или `resume` возвращает собственный ID, роль и текущий снимок со списком участников и вместимостью. Повтор создания или входа с тем же токеном после потери ответа сохраняет место и ID, заменяя предыдущее соединение. Восстановление действует внутри работающего экземпляра клиента и сервера. При явном выходе ведущего сервер завершает комнату для всех слушателей, при обрыве сохраняет её до 90 секунд. Место отключившегося слушателя занимает вместимость до восстановления или истечения того же grace period; явный выход освобождает место сразу.

В комнате ровно из двух участников оба могут сменить роли, если подключены и согласовали с сервером подпротокол `musicsync.roleswap`. Один участник отправляет запрос, второй подтверждает его в течение 30 секунд. Сервер сохраняет код, ID участников, токены и состояние воспроизведения, обновляет роли, увеличивает ревизию и сбрасывает отчёты плееров предыдущей ревизии. В группе из трёх и более мест, включая зарезервированные, эта операция возвращает `role-swap-group-unsupported`; новый механизм передачи управления относится к PR 4.

Команда ведущего несёт ID и базовую ревизию. Сервер последовательно изменяет комнату под короткой общей блокировкой реестра без сетевого ввода-вывода, обновляет ревизию и ставит общий снимок в отдельные ограниченные очереди всех подключённых участников. Сериализация и отправка выполняются вне блокировки; переполнение очереди отключает только медленного клиента. Повтор недавно принятого ID подтверждается без повторного изменения, старая базовая ревизия отклоняется. Принятые изменения переживают разрыв соединения. При потере ответа клиент сверяет новый снимок, автоматического повторения команды нет. Изменения состава и отчётов рассылаются всем без увеличения ревизии воспроизведения.

Снимок включает код, ревизию, номер выбора трека, ID альбома и записи, режим, позицию и отметку сервера. Во время Play позиция растёт от этой отметки. Первое измерение часов выполняется перед применением снимка, далее обмен каждые 2 секунды. Смещение оценивается по четырём отметкам отправки и получения с обеих сторон. Используется выборка с минимальным RTT из последних восьми.

Плеер обрабатывает один снимок за раз. При появлении новой ревизии отложенные шаги старой операции пропускаются. Уже переданный Windows вызов может закончиться, после него применяется актуальный снимок. Подтверждение требует доказательства ID, режима и допустимой позиции. При Play целевая позиция пересчитывается после загрузки. Коррекция при устойчивой работе начинается только при превышении порога или несовпадении режима, с интервалом не менее 8 секунд от предыдущей попытки.

В обычном режиме клиент определяет трек по ссылке в области «Плеер», открытой очереди или карточке с подтверждённым воспроизведением. Наблюдение сверяется с GSMTC. Sonata читает идентификаторы, позицию и режим из состояния плеера через CDP и выбирает треки без открытия карточки. При потере ID слушатель приостанавливает предыдущий подтверждённый трек, если он ещё играет. Состояние неизвестного трека снимается после получения точного ID или нового выбора по ссылке. В конце песни слушатель ждёт следующего трека ведущего.

Разницу между клиентами интерфейс рассчитывает только по свежим подтверждениям одной ревизии при RTT до 400 мс и сопоставимой длительности. Оценка отражает шкалу медиасессий.

## Ограничения протокола

Версия JSON-протокола — 2. Версия 1 и другие версии получают `protocol-version` до входа в комнату, без снимка. Сервер принимает текстовые сообщения до 4096 байт, клиенты — серверные сообщения до 32768 байт: десять отчётов с Unicode могут превысить прежний лимит. Проверяются обязательные поля, допустимые типы и значения, неизвестные и повторные свойства отклоняются. По умолчанию разрешено 32 соединения, 16 комнат и 10 мест в комнате; `Sync:MaxParticipantsPerRoom` допускает значения 1–10. Очередь отправки ограничена 48 сообщениями на клиента. Тайм-аут рукопожатия — 6 секунд, бездействия — 12 секунд, отправки — 4 секунды. При превышении 20 входящих сообщений в секунду или переполнении очереди соединение закрывается. Создание ограничено четырьмя активными комнатами и восемью созданиями за 60 секунд на IP; счётчики также имеют общий предел. Коды и токены хранятся в памяти, отсутствуют в URL и журналах.

Точный контракт для PR 2–4, миграция и бюджет ресурсов: [GROUP_ROOMS_PROTOCOL.md](GROUP_ROOMS_PROTOCOL.md). Интерфейс и алгоритм групповой синхронизации остаются задачами следующих PR.
