# Рекомендации по подключению MusicSync

## Первый прототип

Два Windows-клиента подключаются к одному небольшому серверу MusicSync на существующем VPS. Использовать прямой WSS через отдельный TLS-слушатель, например `wss://sync.<домен>:8443/ws`. DNS-имя указывает на VPS, сертификат проверяется обычным системным хранилищем. Прямой SSH на 443 уже подтверждён, но этот порт занят `sshd`. 8443 отсутствовал среди слушателей, его внешняя доступность пока неизвестна.

```text
ПК A ─── WSS ───┐
                ├── TLS-слушатель VPS ─── MusicSync в отдельной сети
ПК B ─── WSS ───┘
```

Оба клиента сами воспроизводят аудио из Яндекс Музыки. Через сервер проходят только команды синхронизации, ID трека и состояние воспроизведения. Входящий порт на ПК для этой схемы не требуется.

## Изоляция сервиса и доступ

- Выделить отдельный Compose-проект, контейнер, сеть и учётные данные MusicSync. Backend связать с TLS-слушателем через loopback или отдельную сеть. VPS с 1 vCPU и 1161 МиБ доступной RAM в момент проверки подходит для лёгкого двухпользовательского прототипа. Замерить реальные CPU и память при двух подключениях и во время работы бота.
- Проверить доступность одного будущего веб-порта с обеих сетей, правила OneDash и локальную политику firewall. Снимок `UFW inactive` не описывает остальные уровни фильтрации. Начать с 8443, если этот порт можно использовать в обеих сетях.
- Выдать сертификат на имя существующего подконтрольного домена и автоматизировать продление. DNS-01 позволяет выпускать доменный сертификат без входящих 80 и 443 при наличии доступа к DNS. [Проверки ACME Let’s Encrypt](https://letsencrypt.org/docs/challenge-types/)
- Если домена нет и требуется подключение по IPv4, Let’s Encrypt выпускает короткоживущие IP-сертификаты на 160 часов. Для IP подходят HTTP-01 на 80 или TLS-ALPN-01 на 443. При текущем SSH на 443 практически имеет смысл оценить HTTP-01, если 80 можно открыть для проверки и обеспечить автоматическое продление. [IP-сертификаты Let’s Encrypt](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability), [проверки ACME](https://letsencrypt.org/docs/challenge-types/)
- Стандартный 443 для WSS рассматривать после отдельной проверки аутентифицированного SSH на 22 без VPN и консоли восстановления OneDash. Уже подтверждены слушатель 22 на VPS и протокол SSH на 22 через VPN. Если альтернативный доступ не проходит, сохранить текущую схему администрирования и отдельный TLS-порт.

## Что должен уметь сетевой прототип

1. Проверить сертификат и авторизовать каждого клиента случайным токеном комнаты. Ограничить комнату двумя клиентами и размер сообщений. Передавать токен в заголовке или при аутентификации сразу после подключения, хранить его отдельно от адреса и исключить из журналов.
2. Передавать ID трека, позицию в миллисекундах, состояние воспроизведения, порядковый номер и серверную метку времени. Отбрасывать устаревшие события и отправлять свежий снимок состояния при переподключении.
3. Поддерживать heartbeat и переподключение с растущей задержкой. Проверять задержку самого сообщения и фактическое расхождение позиции двух плееров. ICMP и время TCP connect описывают другие участки работы.
4. Проверить с обоих ПК без VPN связку DNS → TCP → TLS → HTTP Upgrade 101 → обмен кадрами в обе стороны. Повторить после простоя и имитации обычного разрыва сети на этапе испытаний. Критерий готовности — оба клиента самостоятельно восстанавливают комнату и актуальное состояние.
5. Контролировать состояние уже запущенного бота по его статусу и метрикам хоста при запуске изолированного прототипа. У прототипа должен быть собственный способ остановки.

## Когда использовать запасной путь

**Cloudflare Tunnel.** Имеет смысл, если обе сети достигают публичного Cloudflare, а до веб-порта VPS одна из них не доходит. Для WSS нужен собственный end-to-end тест и исходящий доступ VPS на 7844. Успешный HTTPS Cloudflare и публичный echo WSS — отдельные проверки. [Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/get-started/), [требования к 7844](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-with-firewall/), [WebSockets](https://developers.cloudflare.com/network/websockets/)

**Tailscale или P2P.** Для двух доверенных ПК Tailscale упрощает закрытую сеть, но добавляет клиентский компонент, координацию и возможный DERP. Чистый P2P потребует измерений NAT/UDP с обеих сторон и отдельной схемы сигнализации или ретрансляции. Обе схемы можно оставить в резерве, пока проверяется прямой WSS на существующем VPS. [Типы соединений Tailscale](https://tailscale.com/docs/reference/connection-types)
