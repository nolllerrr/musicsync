# MusicSync — локальное управление Яндекс Музыкой

Архив раннего прототипа. Команды ниже относятся к той ревизии проекта. [Текущая инструкция к разделу «Вместе»](../docs/TOGETHER.md)

Дата испытаний — 5 ноября 2026 года. Время в протоколе приведено по Москве. Стенд — один ПК с Windows 11 Pro, сборка 26300, русская локаль Яндекс Музыки.

Отдельная программа может запустить конкретную песню в официальной Яндекс Музыке. На установленной версии 5.125.3 нативная ссылка открывает нужную карточку, Windows UI Automation вызывает кнопку этой карточки, а Windows Media Session подтверждает воспроизведение. ID текущего трека также удалось прочитать при обычном переключении в открытой очереди альбома. Для полной синхронизации двух аккаунтов остаётся расширить обнаружение ID на другие режимы и измерить задержку между клиентами.

## Цель и критерии проверки

Проверялось, может ли отдельный процесс на Windows выбрать конкретный трек, запустить его в уже открытой Яндекс Музыке и управлять позицией и состоянием плеера. Это локальный этап MusicSync. Сетевой обмен, координация двух аккаунтов и синхронность аудиовыхода относятся к следующему этапу.

- Команда управления считается выполненной, когда после вызова меняется наблюдаемое состояние целевой медиасессии. Положительный ответ Windows учитывается отдельно.
- Запуск конкретного трека подтверждается парой `albumId` и `trackId` в адресе карточки, состоянием её кнопки «Пауза» и совпадающим названием в системной медиасессии `Playing`.
- Перемотка оценивается по позиции и отметке обновления Windows. Во время воспроизведения позиция продолжает меняться после команды.
- Выводы из установленного пакета и сторонних исходников отмечены отдельно от проверок на ПК. Для неподтверждённых сценариев указано, чего именно не хватает.

### WinYandexMusicRPC

Установлена и запущена версия `3.0` по `C:\Program Files (x86)\WinYandexMusicRPC\WinYandexMusicRPC.exe`. Версию показала запись деинсталлятора. `WindowsMediaSource` перечисляет сессии через GSMTC, берёт метаданные из `TryGetMediaPropertiesAsync`, статус из `GetPlaybackInfo`, позицию, время последнего обновления и длительность из `GetTimelineProperties`. Каталожное совпадение может быть неоднозначным для разных изданий и версий песни. Прототип повторяет подход чтения через Windows собственным кодом. ## B. Способы управления

| Способ | Итог на этом ПК | Возможности и границы |
|---|---|---|
| Windows Media Session (GSMTC/SMTC) | Работает | Состояние, позиция, длительность, `Play`, `Pause`, `Next`, `Previous`, `Seek`. Поддержка `Next` и `Previous` меняется с контекстом. API не публикует ID каталога и содержимое очереди. |
| HTTPS и `yandexmusic://` | Нативный URI открывает карточку | HTTPS направлялся в Firefox. Нативный URI открывал нужный экран существующего клиента. Самостоятельный старт по URL, в том числе с `play=1` и `autoplay=1`, не сработал. |
| UI Automation поверх нативной ссылки | Работает для конкретного трека | Точный маршрут проверяется через `ValuePattern` документа. Кнопка карточки вызывается через `InvokePattern`. После вызова проверяются маршрут, состояние кнопки и GSMTC. В открытой очереди альбома доступна ссылка активной записи. |
| CDP | Живой тест не выполнен | На установленном клиенте локальной точки подключения не было. Возможности изучены по исходникам Music Island. |
| Ynison | Доступен транспорт | На redirector получен WebSocket `HTTP 101` с валидным TLS без авторизации. Доступ к состоянию, команды и поведение целевого устройства в живой учётной записи не проверены. |

### Music Island — Direct Yandex Music

В коммите `73e9f19` `enable` сначала ищет подходящий процесс с `--remote-debugging-port` и проверяет готовность страницы `music-application://` через loopback `/json` и WebSocket. `reattach` переиспользует уже запущенный подходящий endpoint. Если его нет, `enable` подготавливает настройки запуска, останавливает процесс и запускает с `--remote-debugging-port` и `--remote-debugging-address=127.0.0.1`. Код подготовки в Windows умеет менять ярлыки и существующую запись автозапуска. [Подключение и перезапуск](https://github.com/redheadesign/music-island/blob/73e9f194fa48cb2c354a8a7cc9ec277602216474/src-tauri/src/yandex/mod.rs#L320), [подготовка запуска](https://github.com/redheadesign/music-island/blob/73e9f194fa48cb2c354a8a7cc9ec277602216474/src-tauri/src/yandex/launch.rs#L193).

`Runtime.evaluate` читает DOM. ID берётся из ссылки `/track/…` или `data-track-id`, если они есть. Команды нажимают элементы с `data-test-id`: play, pause, toggle, stop как pause, next, previous, like, dislike, shuffle и repeat. Seek изменяет range и посылает события. Есть чтение и выбор пресетов «Моей волны». Команды произвольного трека или записи произвольной очереди в этом адаптере нет. Селекторы, атрибуты и поведение могут измениться при обновлении. Отладчик позволяет выполнять код от имени renderer, поэтому даже loopback без аутентификации доступен другим локальным процессам. [Команды и DOM](https://github.com/redheadesign/music-island/blob/73e9f194fa48cb2c354a8a7cc9ec277602216474/src-tauri/src/yandex/mod.rs#L624), [Electron CLI](https://www.electronjs.org/docs/latest/api/command-line-switches#--remote-debugging-portport), [GPL-3.0-or-later](https://github.com/redheadesign/music-island/blob/73e9f194fa48cb2c354a8a7cc9ec277602216474/LICENSE).

### Yandex Music API и Ynison

В `9ca132e` REST-клиент умеет запрашивать треки и читать очередь по ID. `YnisonClient` держит WebSocket, читает активное устройство, текущий `playable`, прогресс и очередь. Публичные команды клиента — pause, resume, next, previous и громкость. В `set_volume` есть явный `target_device_id`, переключение треков меняет индекс текущей очереди активного устройства. В моделях есть `UpdateActiveDevice`, `UpdatePlayerState` и `UpdatePlayerQueueInject`. Это описания сообщений, по которым нельзя заключить, что сервер примет команду запуска произвольного ID на конкретном настольном клиенте. Клиент отправляет `Authorization: OAuth …`; `HTTP 101` в отдельном пробном запросе без учётных данных подтверждает только доступность WebSocket. Модель устройств и очереди привязана к авторизованной сессии аккаунта. Независимые аккаунты потребовали бы независимого локального управления или отдельных авторизаций и собственной координации. [Команды](https://github.com/MarshalX/yandex-music-api/blob/9ca132e5c18a72aab779c1fc68c169380a9357d0/yandex_music/ynison/client.py#L316), [соединение](https://github.com/MarshalX/yandex-music-api/blob/9ca132e5c18a72aab779c1fc68c169380a9357d0/yandex_music/ynison/_base.py#L237), [модели](https://github.com/MarshalX/yandex-music-api/blob/9ca132e5c18a72aab779c1fc68c169380a9357d0/yandex_music/ynison/models/ynison_state.py#L809), [LGPL-3.0](https://github.com/MarshalX/yandex-music-api/blob/9ca132e5c18a72aab779c1fc68c169380a9357d0/LICENSE).

## C. Прототип

Консольный проект C# для .NET 10 и Windows. `Program.cs` проверяет аргументы, сериализует управляющие команды между экземплярами CLI и возвращает JSON. `YandexClient.cs` проверяет путь процесса и зарегистрированный обработчик URI. `MediaSession.cs` выбирает только точный `SourceAppUserModelId`, опрашивает состояние после команд и даёт сырую позицию `reportedPositionMs` и оценку `positionMs`. `TrackPage.cs` отвечает за нативную ссылку, проверку карточки, семантический `InvokePattern` и подтверждение результата. Для UIA используется проверенная сборка FlaUI.UIA3 5.0.0 из NuGet. Пакеты восстанавливаются в `obj/packages` проекта. `status --track-id` читает уже открытую очередь альбома и возвращает оба каталожных ID при совпадении с медиасессией. [FlaUI.UIA3 5.0.0](https://www.nuget.org/packages/FlaUI.UIA3/5.0.0), [UI Automation Invoke](https://learn.microsoft.com/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomationinvokepattern-invoke), [смысл позиции GSMTC](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessiontimelineproperties.position).

```powershell
Set-Location C:\Projects\musicsync\local-control-poc
dotnet build -c Release
$cli = '.\bin\Release\net10.0-windows10.0.19041.0\musicsync.exe'
& $cli status
# С открытой панелью «Очередь воспроизведения» для трека из альбома
& $cli status --track-id
& $cli pause
& $cli play
& $cli next
& $cli previous
& $cli seek 90000
& $cli play-url 'https://music.yandex.ru/album/10030/track/38634573'
```

`play-url` принимает канонический путь с ID альбома и трека для `https://music.yandex.ru` и `yandexmusic://`. Он использует только числовые ID, проверяет, что клиент уже открыт, и переводит окно на карточку трека. При успехе возвращает `albumId`, `trackId` и состояние `Playing`. Код `0` означает успех, `2` — ошибку аргументов, `3` — отсутствие клиента или сессии, `4` — отказ, недоступный элемент управления или другую ошибку выполнения, `5` — тайм-аут операции. Для `play-url` сессия может появиться уже после вызова кнопки. Требуются права обычного пользователя и интерактивная сессия Windows.

### Как CLI подтверждает результат

| Команда | Что проверяет CLI |
|---|---|
| `status` | Сначала проверяет путь процесса, затем ищет ровно одну сессию `ru.yandex.desktop.music`. В JSON возвращает метаданные, `status`, `durationMs`, `lastUpdatedUtc` и доступность команд в `controls`. |
| `play`, `pause` | Если состояние уже соответствует запросу, возвращает его. Иначе проверяет доступность команды, вызывает GSMTC и ждёт `Playing` или `Paused`. |
| `next`, `previous` | Проверяет изменение метаданных и обновление таймлайна, ждёт устойчивого состояния 600 мс. Для `previous` учитывает случай, когда плеер возвращается к началу того же трека. Две записи с совпадающими метаданными этот способ может не различить. |
| `seek` | Переводит целевую позицию из миллисекунд в единицы WinRT, проверяет диапазон перемотки и ждёт обновления таймлайна текущего трека. Допуск проверки на паузе — 250 мс. При воспроизведении верхняя граница дополнительно учитывает время, прошедшее после вызова. |
| `play-url` | Проверяет обработчик `yandexmusic`, передаёт Windows URI с парой ID и находит карточку в окне клиента. Кнопку вызывает только при точном совпадении маршрута, наличии одного доступного элемента и поддержке `InvokePattern`. Затем проверяет кнопку «Пауза» и медиасессию `Playing`. |
| `status --track-id` | Читает ссылку текущей записи в открытой очереди альбома, сверяет заголовок и перечитывает системную сессию, чтобы обнаружить смену метаданных во время запроса. |

`reportedPositionMs` — позиция из снимка GSMTC относительно начала трека. `positionMs` — оценка позиции на момент чтения. В состоянии `Playing` CLI прибавляет время после `lastUpdatedUtc` с учётом скорости воспроизведения и ограничивает результат длительностью. При отсутствии валидной длительности позиции возвращаются как `null`.

Общий тайм-аут команды — 22 секунды. Для отдельных вызовов GSMTC задано 3 секунды, для опроса подтверждения — 5 секунд. Изменяющие команды сериализованы именованным мьютексом в сессии Windows. Состояние, включая отсутствие клиента или сессии с кодом `3`, выводится в stdout. Ошибки аргументов и выполнения пишутся в stderr. [Таймлайн GSMTC](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssessiontimelineproperties), [позиция в единицах WinRT](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssession.trychangeplaybackpositionasync).

## D. Реальные тесты

| Функция | Результат | Фактическое наблюдение |
|---|---|---|
| Обнаружение клиента и чтение метаданных и длительности | Работает | `ru.yandex.desktop.music`; например «Звезда по имени Солнце», КИНО, `225666.666` мс. `AlbumTitle` был пуст, `TrackNumber` равнялся нулю в сырых пробах. |
| Чтение позиции | Работает | `GetTimelineProperties` возвращал позицию на момент `LastUpdatedTime`. Снимок мог не меняться в течение нескольких секунд и дольше, хотя трек продолжал играть. Оценка `positionMs` учитывает прошедшее время и ограничена длительностью. |
| `pause`, `play` | Работают | `TryPauseAsync` и `TryPlayAsync` вернули `true`, затем наблюдались `Paused` и `Playing`. Команда паузы сразу после перехода в первой пробе вернула `true`, но плеер остался `Playing`, поэтому CLI требует наблюдаемого изменения. |
| `seek` | Работает | На паузе `18 750 → 18 750` и `90 000 → 90 000` мс, оба значения сохранились при следующем чтении. При воспроизведении команда `61 250` дала `61 525.150` мс в первом обновлённом снимке, а `12 500` дала значение примерно на 0,3 с больше. Точность аудиовыхода отдельно не измерялась. [TryChangePlaybackPositionAsync](https://learn.microsoft.com/en-us/uwp/api/windows.media.control.globalsystemmediatransportcontrolssession.trychangeplaybackpositionasync). |
| `next`, `previous` | Работают при доступной очереди | Через GSMTC два `next` сменили `L’amour Toujours` на `meaningful love`, затем на `Ten O’Clock Postman`. `previous` вернул `meaningful love` после переходного `Closed`. В Release CLI последовательность из двух `next` и одного `previous` дала «Будь готов» → «Дворец Пионеров» → «Красный Галстук» → «Дворец Пионеров». ### Сбои и восстановление

- Ранняя проба GSMTC вернула `true` на команду паузы во время перехода между треками, хотя в следующем снимке состояние было `Playing`. В CLI проверяется наблюдаемый результат и отбрасываются переходные снимки.
- При интеграции UIA и GSMTC возникала ошибка COM `0x8001010E`. В итоговой сборке операции UIA выполняются в выделенном MTA-потоке. Повторные переходы и чтение ID подтвердились в Release.
- Эксперимент с прямым URI `yandexmusic://track/151629851` привёл к пустой странице Chromium и исчезновению медиасессии. Пользователь отдельно разрешил штатный перезапуск. Канонические ссылки с двумя ID после него работали. Маршрут только с ID в CLI не используется.

После разрешённого восстановления проверялся процесс PID `23424`. Он оставался тем же при переключениях по URL, флагов отладки и TCP-слушателей не обнаружено. В конце открыта «Моя волна», воспроизведение на паузе. В плеере осталась загружена последняя тестовая песня, тогда как до тестов медиасессии не было.

## E. Ограничения

`play-url` и `status --track-id` зависят от структуры accessibility-дерева и локализованных названий элементов. Для `play-url` также важна доступность карточки на аккаунте. Проверена русская локаль клиента 5.125.3. Команда открывает карточку и может вывести окно на передний план. Путь с альтернативным ID, который Яндекс заменяет каноническим, завершается без вызова кнопки для несовпавшего ID. Недоступный трек, смена интерфейса и потеря сессии приводят к отказу или тайм-ауту. Повтор после тайм-аута требует сверить `status`, поскольку отдельный вызов мог быть принят плеером до истечения срока подтверждения.

На одном ПК подтверждена работоспособность внешнего управления без патча. `play-url` переводит выбранный трек в `Playing`, поэтому при переходе на другой трек для комнаты на паузе возможен короткий старт перед вызовом `pause`. Отдельный режим предварительной загрузки без воспроизведения в этом прототипе не проверялся. Тесты между двумя ПК, двумя аккаунтами, в заблокированном сеансе Windows и измерения рассинхронизации по аудиовыходу не проводились. Переиспользование CDP требует уже существующей loopback-точки подключения или отдельно согласованного запуска с флагами.

## F. Что можно синхронизировать

| Данные или действие | Текущая возможность |
|---|---|
| Текущий трек | У ведущего доступны метаданные и события GSMTC. ID можно получить в открытой очереди альбома. При известном каноническом URL ведомый может точно запустить трек. Для «Моей волны», других контекстов и закрытой панели нужен дополнительный источник ID. |
| Пауза и продолжение | Проверены локально. |
| Перемотка и подключение посреди трека | Локальная операция проверена. Ведомый сможет применить актуальную позицию после подтверждения нужной песни. Сетевой сценарий требует проверки. |
| Следующий трек | Локальная команда работает в доступной очереди. Для двух аккаунтов надёжнее отправить ID/URL фактически выбранной песни, поскольку «Моя волна» и очереди могут различаться. |
| Произвольная песня | Проверена по каноническому URL и с подтверждением активной карточки. |
| Очередь | Пассивное чтение и произвольная запись штатной очереди не подтверждены. Комнатную очередь можно вести в MusicSync и выбирать конкретный URL на каждом шаге. |

## G. Следующий этап

Отдельный Windows-клиент держит исходящее соединение с WebSocket-сервером MusicSync. Оба клиента воспроизводят через свои локальные аккаунты. Сервер хранит последний снимок комнаты с `revision`, `albumId`, `trackId`, `positionMs`, временем снимка и статусом паузы. Ведомый применяет снимок по порядку, сначала подтверждает трек, затем вычисляет и выставляет позицию с учётом времени, после чего подтверждает состояние. Более свежая ревизия вытесняет устаревшую. Допуск коррекции стоит подобрать по измеренной задержке старта, перемотки и аудиовыхода на двух машинах.

Первую проверку на двух аккаунтах можно провести с выбором песни из MusicSync или по переданному каноническому URL. Параллельно нужно проверить, можно ли читать ID в «Моей волне», плейлистах и при закрытой панели очереди. Для альбомной очереди уже есть проверенный путь через ссылку активной записи. Неоднозначные совпадения по названию и исполнителю требуют явного выбора. Для строгой синхронизации очереди оба клиента могут принимать следующие URL из состояния комнаты.

### Что проверить на двух ПК

| Сценарий | Что фиксировать |
|---|---|
| Смена песни у ведущего | Совпадение пары `albumId` и `trackId` на обеих сторонах и время от смены до подтверждения ведомым. |
| Подключение во время воспроизведения | Позиция с учётом времени снимка и разница между клиентами после старта. Отдельно измерить реальный аудиовыход. |
| Пауза, продолжение и перемотка | Итоговое состояние и позиция на обеих машинах, включая смену трека при паузе комнаты. |
| Повторная доставка и потеря связи | Как ведомый применяет последнюю ревизию, отбрасывает устаревшую и восстанавливается по снимку комнаты. |
| Недоступный трек или закрытый клиент | Как клиент сообщает о причине отказа и возвращается к работе после восстановления. |
| «Моя волна», плейлист и закрытая очередь | Можно ли получить точный ID без сопоставления треков только по метаданным. |

Предлагаемый результат первого сетевого этапа — запуск известной канонической пары ID на двух отдельных аккаунтах, синхронизация паузы и позиции и измеренный разброс на аудиовыходе. Порог приемлемой рассинхронизации определяется после этих измерений.
